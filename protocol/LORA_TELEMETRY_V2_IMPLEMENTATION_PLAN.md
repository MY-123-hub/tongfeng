# LoRa遥测协议V2实施计划

## 1. 文档状态

- 状态：待执行计划，尚未按本计划修改业务代码。
- 设计依据：[`LORA_TELEMETRY_V2_DESIGN.md`](./LORA_TELEMETRY_V2_DESIGN.md)。
- 实施范围：从机、主机 `_TD710`、控制室、上位机及其测试。
- 目标设备：M1/S1～M4/S4四组，使用相同固件逻辑，只通过组号区分。
- 新增范围：每个从机PB1雨滴传感器在第二帧预留2 B；硬件尚未测试，当前只发送无效占位值。
- 当前正式协议仍为V1；V2四端全部验收通过后再统一切换。

## 2. 实施结论

本次改造不得一次性同时修改四端后再联调。按以下顺序执行：

```text
基线和测试入口
→ 从机传感器采集能力
→ V2公共协议与标准测试向量
→ 从机V2响应
→ 主机V2中继和BME补位
→ 控制室四组轮询
→ 上位机解析、显示和存储
→ 单组整链路
→ 四组整链路
→ 统一切换V2
```

其中，从机湿度采集是第一项业务改动。在从机不能稳定给出36个固定槽位的温度、湿度及本机BME数据之前，不进入LoRa数据帧改造。

## 4. 阶段0：冻结V2协议和标准向量

### 4.1 工作内容

1. 复核并冻结V2消息类型、字段偏移、数据长度、字节序和无效值。
2. 为四端建立同一组标准十六进制测试向量：
   - M1～M4温度请求。
   - M1～M4湿度/气压请求。
   - 温度响应：正常值、负温度、`0.0℃`、无效值。
   - 湿度/气压/雨滴响应：`0.0%RH`、正常值、上下限和各类无效值。
   - CRC错误、错误长度、错误版本、错误角色和错误组号。
3. 明确V2切换策略：正式系统停机后四端统一升级，不在生产链路混跑V1和V2。
4. 在正式切换时把 `protocol/LORA_TELEMETRY.md` 更新为当前生效的V2协议；设计阶段仍保留V1正式状态说明。

### 4.2 验收条件

- 四端针对同一测试向量得到完全相同的CRC和字段值。
- 温度响应固定89 B，湿度/气压/雨滴响应固定99 B。
- 所有响应均小于109 B应用帧上限和128 B LoRa MTU。
- `0.0℃`与`0.0%RH`作为合法值通过测试。

## 5. 阶段1：从机传感器采集改造

### 5.1 目标

先让正式从机工程稳定生成完整的本地遥测快照，不涉及主机、控制室和上位机。

建议建立统一的从机快照结构，至少包含：

```c
int16_t  node_temperature_x10[36];
uint16_t node_humidity_x10[36];
int16_t  slave_bme_temperature_x10;
uint16_t slave_bme_humidity_x10;
uint32_t slave_bme_pressure_pa;
uint16_t rain_value;
uint32_t sample_tick;
```

同时保留每个字段或每类数据的有效状态，不能只用一个总有效标志掩盖局部传感器故障。

### 5.2 GXHT3W处理

重点检查和修改：

- `从机/Bsp/bsp_ds18b20.c`
- `从机/Bsp/bsp_ds18b20.h`
- `从机/Core/Src/main.c`

正式代码现状是 `GXHT3W_Read_TempHum()` 已能返回温度和湿度，但 `main.c` 只保留温度，局部变量 `humidity` 随后被丢弃。实施时应：

1. 参考 `LoraSlave.switch match` 中已验证的读取和换算方式。
2. 一次GXHT3W读取同时保存温度和湿度。
3. 保持六端口、每端口六槽位的固定顺序。
4. DS18B20槽位的湿度固定为 `0xFFFF`。
5. 空槽、ROM错误、CRC错误、超范围值使用协议无效值，后续传感器不得向前补位。
6. 修正当前把 `0.0℃`判为无效的逻辑；V2中零温度是合法值。

### 5.3 从机BME280处理

正式从机已初始化BME280，但尚未把测量结果加入业务快照。实施时调用现有 `BME280_ReadAll()`，并严格换算：

| 驱动输出 | 快照输出 |
|---|---|
| 温度 `℃×100` | 四舍五入为 `℃×10` |
| 湿度 `%RH×1024` | 四舍五入为 `%RH×10` |
| 气压 `Pa` | 保持 `Pa` |

必须分别验证温度、湿度和气压范围。BME故障时只把BME三个字段设为无效，不得清除36路节点数据。

### 5.4 雨滴传感器预留

每个从机预留一个PB1雨滴传感器字段。由于传感器尚未完成硬件测试，本批次不配置PB1、不启用ADC或GPIO读取，也不定义干湿方向和阈值：

- 快照中的 `rain_value` 固定为 `0xFFFF`。
- 第二帧始终保留2 B，后续启用传感器时不再改变帧长。
- 若后续确认使用PB1的ADC功能，2 B可容纳12位原始采样值。
- 若后续确认使用数字输出，可在协议补充中定义0/1含义，字段宽度保持不变。
- 在电气接口、阈值和实测结果确认前，上位机只能显示“未启用”，不得解释为有雨或无雨。

### 5.5 采样状态机

- 传感器采集与LoRa请求解耦，后台持续更新快照。
- 保留1-Wire转换等待的非阻塞状态机，禁止在协议处理路径增加长时间 `HAL_Delay()`。
- GXHT3W和DS18B20共存时按ROM家族码分别解析。
- 新快照完整生成后再原子替换活动缓存，禁止通信任务读到更新一半的数组。

### 5.6 阶段验收

通过串口诊断或调试器验证以下组合：

1. 单个GXHT3W。
2. 每个端口各一个GXHT3W。
3. 单端口六个GXHT3W。
4. GXHT3W和DS18B20混接。
5. 传感器缺失、CRC错误、运行时拔插。
6. BME280正常、断开和恢复。
7. `0.0℃`、`0.0%RH`及负温度的编码。

本阶段通过标准是：连续采集不少于1000轮，无数组越界、死循环和槽位移动，湿度与参考仪表变化趋势一致。

## 6. 阶段2：从机V2协议响应

### 6.1 修改范围

- `从机/App/slave_protocol_runtime.c`
- `从机/App/slave_protocol_runtime.h`
- `从机/Core/Src/main.c`
- 从机协议主机测试及伪硬件接口

### 6.2 工作内容

1. 协议版本升级为 `0x02`。
2. 支持四种遥测消息：`0x01`～`0x04`。
3. 温度请求返回76 B数据区：36路温度、从机BME温度、主机BME温度无效占位。
4. 湿度/气压请求返回86 B数据区：36路湿度、从机BME湿度、主机BME湿度无效占位、从机BME气压、主机BME气压无效占位及从机雨滴 `0xFFFF`占位。
5. 自动请求的 `read_mode=0x00`读取最新缓存；强制采样 `0x01`使用独立状态，不阻塞协议解析。
6. 重复 `flow_id`重发对应类型的最近完整响应；温度和湿度/气压分别维护重复请求记录，不能互相覆盖。
7. 只响应同组主机请求，M1/S1～M4/S4执行相同逻辑。

### 6.3 阶段验收

- C单元测试逐字节核对两类响应及CRC。
- 错误组号、角色、版本、长度和类型全部被拒绝。
- 连续交替请求两类数据不会串帧或返回错类型。
- 温度帧丢失不影响湿度/气压帧，反之亦然。

## 7. 阶段3：主机V2中继和本机BME补位

### 7.1 修改范围

- `主机_TD710/App/lora_protocol.c/.h`
- `主机_TD710/App/master_runtime.c/.h`
- `主机_TD710/App/master_messages.h`
- `主机_TD710/App/master_config.h`
- `主机_TD710/App/master_temperature.c/.h`
- 建议新增 `master_environment.c/.h`，避免把湿度/气压状态强行塞入温度服务。
- `主机_TD710/Core/Src/freertos.c`
- 对应主机单元测试

### 7.2 工作内容

1. 协议编解码器升级V2并增加新消息类型、方向和严格长度校验。
2. 保留现有主机BME后台任务，统一其缓存新鲜度和无效值规则。
3. 温度事务和湿度/气压事务分别维护状态、流水号、缓存时间和超时。
4. 收到从机温度响应后，保留36路温度及从机BME温度，写入主机BME温度预留位置。
5. 收到从机湿度/气压响应后，保留36路湿度、从机BME湿度/气压和雨滴预留值，写入主机BME湿度、气压预留位置。
6. 主机BME缓存无效或过期时写入协议无效值，不得阻止从机数据继续转发。
7. 补位和地址改写后重新编码整帧并计算CRC。
8. 自动风机控制仍只依赖36路节点温度缓存，不等待湿度/气压帧。

### 7.3 阶段验收

- 主机只修改设计规定的主机BME字段和地址字段。
- 从机字段在中继前后逐字节一致。
- 主机BME正常、无效和过期三种情况均有测试。
- 两类事务并发到达时返回BUSY或进入既定队列，不破坏单事务规则。
- 原有变频器命令、自动控制和参数保存测试全部继续通过。

## 8. 阶段4：控制室四组通用轮询

### 8.1 修改范围

- `控制室/控制室/Bsp/lora_protocol.h`
- `控制室/控制室/Bsp/gateway_runtime.c/.h`
- 控制室网关主机测试

### 8.2 工作内容

1. 协议版本和消息类型升级为V2。
2. 删除当前只接受 `GATEWAY_ACTIVE_GROUP=1` 的单组限制。
3. 建立1～4活动组列表和当前位置状态，不为任何组编写专用分支。
4. 使用统一队列执行：

```text
M1温度 → M1湿度/气压 → M2温度 → M2湿度/气压
→ M3温度 → M3湿度/气压 → M4温度 → M4湿度/气压
```

5. 每次只保留一个待完成事务，按组号、响应类型和 `flow_id`三项匹配。
6. 当前事务成功、返回错误或超时后才进入下一项。
7. 单组故障不能阻塞其他组；迟到响应不得结束新的事务。
8. 控制室只验证和转发数据，不拼接两类响应，也不修改传感器字段。

### 8.3 阶段验收

- 活动组数量分别为1、2、3、4时，轮询顺序和回绕均正确。
- 任意一组超时后下一组仍被轮询。
- 错组、错类型、错流水号响应不能错误结束当前事务。
- 手动命令插队完成后，自动轮询从正确位置继续。
- 连续1000个四组循环无组饥饿、队列溢出和帧混淆。

## 9. 阶段5：上位机V2解析、显示和存储

### 9.1 修改范围

- `上位机/main.py`
- `上位机/tests/test_protocol.py`
- `tests/test_upper_protocol.py`

建议在实施时先从 `main.py` 抽出纯协议模块，减少GUI导入对单元测试的干扰，但不在本计划阶段提前重构无关界面。

### 9.2 工作内容

1. 升级V2版本、消息类型、请求构造和严格长度检查。
2. 为组1～4分别保存：
   - 36路节点温度。
   - 36路节点湿度。
   - 从机BME温度、湿度、气压。
   - 主机BME温度、湿度、气压。
   - 从机雨滴预留值；正式启用前显示为“未启用”。
   - 两类数据各自的接收时间和有效状态。
3. 温度帧到达时只更新温度相关字段。
4. 湿度/气压帧到达时只更新湿度和气压相关字段。
5. 无效值显示为“无数据”或 `--`，不得显示为极端数值。
6. 两类帧不要求相邻、同流水号或同时到达。
7. 数据导出保留组号、传感器来源和单位。

### 9.3 数据库审批门

当前SQLite表已有 `rain`字段，可暂存以后定义的雨滴值，但只有一组 `humidities` 和一个 `pressure`字段，无法明确表达从机BME与主机BME的两套温湿度气压来源。正式持久化仍需要调整数据库结构或建立V2新表，这属于数据库schema变更。

根据项目红线，执行数据库schema修改或迁移前必须单独向用户说明拟采用的表结构、旧数据兼容方式和回退方案，并取得明确同意。在获得同意前，可以完成协议解析和内存显示，但不得修改现有数据库schema。

### 9.4 阶段验收

- Python测试使用标准向量核对两类帧、CRC、负温度和无效值。
- M1～M4数据进入各自模型，互不覆盖。
- 任意一类帧单独丢失时，另一类仍正常更新。
- 界面明确区分节点、从机BME和主机BME。
- 历史数据读取和命令日志功能不因V2解析而失效。

## 10. 阶段6：分层整链路联调

### 10.1 联调顺序

严格按以下顺序扩大范围，前一级未通过不得进入下一级：

1. 模拟报文 → 单端协议解析。
2. S1 → M1。
3. S1 → M1 → 控制室。
4. S1 → M1 → 控制室 → 上位机。
5. 复制同一固件并只修改拨码，依次验证组2、组3、组4。
6. M1/S1～M4/S4同时在线，执行完整八事务循环。

### 10.2 四组验收矩阵

每组都必须验证：

- 36路槽位顺序一致。
- GXHT3W温度、湿度同时有效。
- DS18B20温度有效、对应湿度为无效值。
- 从机BME三项位置正确。
- 主机BME三项位置正确。
- 雨滴字段固定处于第二帧末尾，当前为 `0xFFFF`，中继过程中保持不变。
- 从机不具备的主机字段在到达主机前为无效值。
- 主机补位后CRC正确。
- 控制室和上位机不改变数值与组号。

故障测试包括：

- 单个传感器失效。
- 单组从机断电。
- 单组主机断电。
- BME280断开。
- CRC错误、截断帧、粘包、拆包。
- 重复请求、重复响应和迟到响应。
- `flow_id`从 `0xFFFF`回绕到 `0x0000`。

### 10.3 性能记录

当前不把固定毫秒数写死为协议要求。实机记录一个完整八事务循环的：

- 平均周期。
- 最大周期。
- 单事务平均与最大往返时间。
- 超时、重试和CRC错误数。
- 四组各自的数据最大陈旧时间。

测试结果用于确定最终自动轮询超时和缓存新鲜度参数，四组必须使用同一组配置。

## 11. 阶段7：构建、发布前检查和切换

### 11.1 自动验证

每个阶段至少运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\tests\host\run_tests.ps1
python -m unittest discover -s .\上位机\tests -p "test_*.py"
python .\tests\test_upper_protocol.py
```

测试脚本路径修复后，C测试必须在 `-O0`和 `-O2`下以严格警告通过。三个STM32工程分别使用各自的Keil工程完整编译，并记录0错误、0警告或逐项解释已有警告。

### 11.2 切换顺序

V1与V2版本号不同，正式切换期间不允许把通信失败误判为设备故障。建议：

1. 停止自动风机控制并确认变频器处于安全状态。
2. 保存四端最后一版V1可恢复固件和上位机程序。
3. 依次升级四台从机、四台主机、控制室，最后切换上位机。
4. 先只启用组1做冒烟测试，再逐个启用组2～4。
5. 四组全部通过后恢复自动控制。

现场烧录和切换属于独立执行步骤，应在代码、测试和台架联调完成后进行，不与开发修改混在同一阶段。

## 12. 完成定义

只有同时满足以下条件，V2改造才算完成：

- 协议文档、四端常量、字段偏移和CRC完全一致。
- 正式从机能够采集并缓存GXHT3W湿度及从机BME三项数据。
- 两类响应固定为89 B和99 B，并通过标准向量。
- 主机正确补入本机BME字段，未破坏从机字段。
