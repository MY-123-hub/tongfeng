二、硬件连接

外设STM32 引脚波特率用途
USART1PA9 (TX) / PA10 (RX)115200连接 DGUS 触摸屏
USART2PA2 (TX) / PA3 (RX)115200连接 LoRa 无线模块
USART3PB10 (TX) / PB11 (RX)9600RS485 Modbus 变频器

DGUS 屏通信电平为 TTL（3.3V / 5V 兼容），与 STM32 的 USART1 直连，无需 RS232 电平转换。

二、DGUS 通信协议

DGUS 屏使用迪文自家指令集，数据帧格式如下：

字节偏移0-1234-56-7
含义帧头 0x5A 0xA5数据长度指令 0x82（写变量）变量地址（大端）数据（大端）
指令 0x82 — 写变量存储区
DGUS 屏内部有一块变量存储空间（地址 0x0000–0xFFFF），每个地址存 2 字节数据。向某个地址写入数据，屏幕对应控件就会自动刷新显示。

例如：向 0x3102 写入 0x0019（即 25℃），屏幕上的"粮面温度"控件就会显示 25.0℃。

接收状态宏

#define REV_WAIT    1                  // 接收未完成 — 数据还在传输中
#define REV_OK      0                  // 接收完成 — 一帧数据已收齐

这两个宏是 DGUS 串口通信的状态判断基础。由于 USART 是逐字节中断接收，程序通过比较两次检查之间接收指针是否变化，来判断一帧数据是否传输完毕。

DGUS 屏幕变量地址枚举

typedef enum
{
    DGUS_GrainHumi     = 0x3100,       /* 粮面湿度  — 屏幕地址 0x3100 */
    DGUS_GrainTemp     = 0x3102,       /* 粮面温度  — 屏幕地址 0x3102 */
    DGUS_GrainSpeed    = 0x3104,       /* 粮面风速  — 屏幕地址 0x3104 */
    DGUS_EnvirHumi     = 0x3106,       /* 环境湿度  — 屏幕地址 0x3106 */
    DGUS_EnvirTemp     = 0x3108,       /* 环境温度  — 屏幕地址 0x3108 */
} DGUSWriteAddrTypeNum;

每个地址间隔 2 字节（0x3100 → 0x3102 → 0x3104 …），因为 DGUS 每个变量地址占 2 字节。这些地址与屏幕 UI 工程中的控件绑定——屏幕设计师在 DGUS 软件里把"温度显示"控件绑到 0x3102，STM32 往这个地址写数据，控件就自动刷新。

4.2 DGUS.c — 驱动实现

📄 Bsp/DGUS.c

4.2.1 全局变量

uint16_t DGUS_cntPre = 0;               // 上一次检查时的接收指针快照

用于配合 rx1_pointer 判断接收是否完成（两者相等 → 指针不再增长 → 接收完毕）。

4.2.2 DGUS_Clear — 清空接收缓存

void DGUS_Clear(void)
{
    memset(Rx1Buffer, 0, sizeof(Rx1Buffer));  // 将 USART1 接收缓冲区全部置零
    rx1_pointer = 0;                            // 接收指针归零，从头开始收新一帧
}
行说明
memset(Rx1Buffer, 0, …)把 100 字节的接收缓存全部填 0。发送新指令前必须清空，否则残留的旧数据会干扰 WaitRecive 的判断逻辑
rx1_pointer = 0接收写指针回到数组头部。后续 USART1 中断会把新收到的字节从 Rx1Buffer[0] 开始存放

4.2.3 DGUS_WaitRecive — 等待接收完成（核心）

_Bool DGUS_WaitRecive(void)
{
    if(rx1_pointer == 0)                    // [1] 还没收到任何数据
        return REV_WAIT;                     //     → 直接返回"未完成"

    if(rx1_pointer == DGUS_cntPre)        // [2] 指针和上一次快照相同
    {                                        //     → 可能接收已停止
        HAL_Delay(5);                       // [3] 等 5ms —— 消抖确认
        if(rx1_pointer == DGUS_cntPre)      // [4] 5ms 后指针依然没变
        {                                    //     → 确认接收完毕
            rx1_pointer = 0;                // [5] 归零指针，准备处理数据
            return REV_OK;                   // [6] 返回"接收完成"
        }
    }
    DGUS_cntPre = rx1_pointer;              // [7] 保存当前指针快照，供下次比较
    return REV_WAIT;                        // [8] 返回"未完成"
}
🔑 核心算法：指针停滞检测法
这个函数判断"一帧数据是否收完"的思路非常经典：

原理：串口数据是逐字节到达的。数据在传输时，rx1_pointer 会不断增长。当发送方停止发送后，指针停止增长。程序记录上一次的指针值 DGUS_cntPre，如果两次检查指针没变（且经过 5ms 消抖），说明发送方已经发完——这一帧收齐了。

5ms 延时的作用：防止误判。比如在两次检查的间隙刚好所有数据到达，指针相同但其实是巧合。等 5ms 再查一次，如果还是相同，才能确认真的收完了。

4.2.4 DGUS_WriteSingleData — 向屏幕写单个数据

void DGUS_WriteSingleData(int S_Addr, int Data)
{
    char Com_all[16] = {
        0x5A, 0xA5,                      // [1] 帧头
        0x05,                            // [2] 数据长度 = 5 字节（指令1 + 地址2 + 数据2）
        0x82,                            // [3] 写变量存储区指令
        S_Addr/256, S_Addr%256,        // [4] 变量地址（拆成高字节 + 低字节，大端序）
        Data/256,   Data%256          // [5] 数据值（拆成高字节 + 低字节）
    };

    DGUS_Clear();                       // [6] 发前先清空接收缓存
    Usart_SendString(huart1,            // [7] 通过 USART1 发送 8 字节指令
        (unsigned char *)Com_all, 8);
}
字节值含义
0–10x5A 0xA5DGUS 帧头，所有指令固定以此开头
20x05后面还有 5 字节（指令 1B + 地址 2B + 数据 2B）
30x82指令码：写变量存储区
4–5S_Addr/256, S_Addr%256变量地址，大端序。如 0x3102 → 0x31, 0x02
6–7Data/256, Data%256数据值，大端序。如 250 (0x00FA) → 0x00, 0xFA
📐 大端序拆分
DGUS 协议要求多字节数据按大端序（Big-Endian）传输，即高字节在前。

S_Addr / 256 = 整除 256，得到高 8 位（相当于右移 8 位）
S_Addr % 256 = 取模 256，得到低 8 位

例：地址 0x3102 → 0x3102 / 256 = 0x31，0x3102 % 256 = 0x02

4.2.5 DGUS_TouchAck — 触摸按键应答（LoRaTask 中调用）

⚠️ 注意
虽然这个函数写在 DGUS.c 里，但它在 LoRaTask（1ms 周期）中被调用，而不是 DGUSTask。DGUSTask 只负责定时刷新屏幕数据。 
void DGUS_TouchAck(void)
{
    if((DGUS_WaitRecive() == REV_OK) &      // [1] 先确认收到一帧完整数据
       (Rx1Buffer[0] == 0x5A) &               // [2] 且帧头第1字节 = 0x5A
       (Rx1Buffer[1] == 0xA5))                 // [3] 且帧头第2字节 = 0xA5 → 是有效DGUS帧
    {
        if(Rx1Buffer[3] == 0x83)              // [4] 指令码 = 0x83 → 触摸坐标数据上报
        {

DGUS 屏被触摸后，会自动通过串口上报一帧数据，格式如下：

字节0–1234–56–7
值0x5A 0xA5长度0x83（触摸上报）触点 X 坐标触点 Y 坐标

系统通过判断触摸坐标来识别用户按了哪个按钮：

        if((Rx1Buffer[4] == 0x29) & (Rx1Buffer[5] == 0x00))  // 坐标 (0x29, 0x00)
        {                                                        // → 用户按了"降水模式"按钮
            DGUS_Clear();
            char Com_all[20] = { 0x5A, 0xA5, 0x09, 0x82,
                0x29, 0x00,                               // 地址 0x2900
                0x00, 0x01, 0x00, 0x00, 0x00, 0x00 };  // 降水=1, 降温=0, 储冷=0
            Usart_SendString(huart1, …);               // 回写屏幕，切换UI状态
        }
触控坐标对应按钮执行动作
0x29, 0x00模式设定 → 降水模式回写地址 0x2900，设降水=1
0x29, 0x01模式设定 → 降温模式回写地址 0x2900，设降温=1
0x29, 0x02模式设定 → 储冷模式回写地址 0x2900，设储冷=1
0x29, 0x03–0x08品种选择（6 种粮食）回写地址 0x2903，设对应品种位=1
🔑 触摸应答机制的本质
DGUS 屏的按钮按下后会自动上报坐标 + 自动切换按钮的按下/弹起状态。但"模式选择"这类业务逻辑需要互斥——选了降水就不能同时选降温。

所以 STM32 收到触摸上报后，重新发送一帧写指令覆写对应地址，在单片机端实现互斥逻辑。这就是"应答"的含义——不是简单回一个 ACK，而是主动重写屏幕变量来矫正 UI 状态。

4.3 StartDGUSTask — FreeRTOS 显示屏任务

📄 Core/Src/freertos.c（第 187–201 行）
/**
 * @brief  任务：更新 DGUS 的环境数据
 *          执行周期：5s
 */
void StartDGUSTask(void const * argument)
{
    for(;;)                                     // [1] FreeRTOS 任务死循环
    {
        DGUS_WriteSingleData(DGUS_GrainTemp,     // [2] 粮面温度 → 地址 0x3102
            LoRaType.DS18B20_Data[0]);        //     数据来源：第1路DS18B20

        DGUS_WriteSingleData(DGUS_EnvirHumi,     // [3] 环境湿度 → 地址 0x3106
            LoRaType.DHT11_Humi);               //     数据来源：DHT11湿度值

        DGUS_WriteSingleData(DGUS_EnvirTemp,     // [4] 环境温度 → 地址 0x3108
            LoRaType.DHT11_Temp);               //     数据来源：DHT11温度值

        DGUS_WriteSingleData(DGUS_GrainSpeed,    // [5] 粮面风速 → 地址 0x3104
            LoRaType.WindPressure);             //     数据来源：风压传感器

        osDelay(5000);                           // [6] 阻塞 5 秒（5000 个 FreeRTOS tick）
    }
}

逐行解析

行代码解析
[1] for(;;) FreeRTOS 任务必须是永不退出的无限循环。任务函数一旦 return，RTOS 内核会把该任务视为"自杀"，之后不会再调度它
[2] DGUS_WriteSingleData(DGUS_GrainTemp, LoRaType.DS18B20_Data[0]) 向屏幕地址 0x3102 写入第 1 路 DS18B20 温度值。
DS18B20_Data[0] 原始值是实际温度 × 10（如 25.3℃ → 253），屏幕端 UI 工程配置了小数点位数，自动显示为 25.3
[3] DGUS_WriteSingleData(DGUS_EnvirHumi, LoRaType.DHT11_Humi) 向地址 0x3106 写入环境湿度（%RH）
[4] DGUS_WriteSingleData(DGUS_EnvirTemp, LoRaType.DHT11_Temp) 向地址 0x3108 写入环境温度
[5] DGUS_WriteSingleData(DGUS_GrainSpeed, LoRaType.WindPressure) 向地址 0x3104 写入风压值
[6] osDelay(5000) 让任务进入阻塞态 5 秒。阻塞期间 CPU 自动调度其他任务（LoRaTask、ModBusTask）执行。
注意：osDelay 不是忙等——它调用 vTaskDelay，将任务移入延时链表，完全释放 CPU
⚠️ 为什么是 5 秒刷新一次？
粮仓温度、湿度是慢变量——几分钟才变化零点几度。每秒刷新只会增加串口通信负担，对实际使用毫无意义。

5 秒是在"数据及时性"和"通信开销"之间的工程权衡。如果对实时性有更高要求（如调试阶段），可改为 osDelay(1000)（1 秒刷新）。

4.4.1 USART1 初始化

void MX_USART1_UART_Init(void)

4.4.2 Usart_SendString — 发送函数

void Usart_SendString(UART_HandleTypeDef USARTx,
                      unsigned char *str, unsigned short len)
{
    unsigned short count = 0;
    for(; count < len; count++)
    {
        HAL_UART_Transmit(&USARTx,           // 逐字节发送
            (uint8_t *)str++, 1, HAL_MAX_DELAY); // 每次发1字节，阻塞等待完成
    }
}
🔑 为什么逐字节发送而不是 DMA？
本项目 DGUS 通信数据量极小（每帧最多 16 字节，每 5 秒发 4 帧共 32 字节），逐字节轮询发送简单可靠。

HAL_MAX_DELAY 表示无限等待——如果发送寄存器一直不空（硬件故障），函数会永远阻塞。生产环境中可改为有限超时（如 100ms）并检查返回值。

4.4.3 USART1 中断接收回调

uint8_t Rx1Buffer[100];                   // USART1 接收环形缓冲区
uint8_t rx1_pointer;                     // 写指针
uint8_t rx1_data;                        // 单字节接收暂存

void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    if(huart->Instance == USART1)
    {
        Rx1Buffer[rx1_pointer++] = rx1_data;   // 存入缓冲区，指针后移
        HAL_UART_Receive_IT(&huart1,            // 重新使能中断接收下一个字节
            &rx1_data, 1);                   // （STM32 HAL 每次中断只收1字节）
    }
}
⚠️ 缓冲区溢出风险
Rx1Buffer 只有 100 字节，且没有环形回绕逻辑（rx1_pointer 只增不减，只有 DGUS_Clear() 时归零）。

如果上位机连续发送超过 100 字节而不给单片机清缓存的机会，rx1_pointer 会越界写坏相邻内存。这是已知的技术债——正常使用时 DGUS 上报帧很短（约 8 字节），不会触发此问题。

4.5 数据结构 — 数据从哪来

📄 Bsp/lora.h
typedef struct
{
    volatile int DS18B20_PORT, DS18B20_NUM;  // DS18B20 端口号 / 传感器数量
    volatile int DS18B20_Data[8];           // 最多 8 路温度值
    volatile int DHT11_Humi, DHT11_Temp;     // DHT11 湿度 / 温度
    volatile int WindPressure;               // 风压传感器
} LoRaTypeDef;

LoRaType 是全局实例，在 LoRaTask（1ms 周期）中由 LoraP2PRX() 持续更新。DGUSTask 只读不写——这是一个生产者-消费者模型，没有用互斥锁保护（因为写入是整字对齐的 int，ARM Cortex-M3 单拷贝原子性保证不会读到"半新半旧"的值）。

五、任务调度全景

系统 4 个任务的优先级和周期：

任务优先级周期职责
StartDefaultTaskosPriorityNormal1ms空转（预留）
StartLoRaTaskosPriorityIdle~1msLoRa 收发 + 通风判断 + 触摸应答
StartDGUSTaskosPriorityIdle5s更新屏幕显示数据
StartModBusTaskosPriorityIdle1sModbus 变频器通信
🔑 为什么所有任务都是 osPriorityIdle？
在 STM32CubeMX + CMSIS-RTOS v1 中，osPriorityIdle 映射到 FreeRTOS 优先级 0（最低）。所有任务同优先级意味着时间片轮转调度（configUSE_TIME_SLICING = 1）：

每个任务运行一个 tick（1ms）后，如果有同优先级的就绪任务，内核强制切换。但因为 DGUSTask 和 ModBusTask 大部分时间在 osDelay 阻塞，实际上 LoRaTask 几乎独占 CPU——这正好满足了 LoRa 通信对实时性的要求。

改进建议：将 LoRaTask 提升到 osPriorityAboveNormal，确保无线数据不丢包。

六、完整数据流时序

时刻 0ms  ─── LoRaTask: LoraP2PRX() 接收传感器数据 → 更新 LoRaType 结构体
时刻 0ms  ─── DGUSTask: DGUS_WriteSingleData(粮温) → USART1 发 8 字节
时刻 0ms  ─── DGUSTask: DGUS_WriteSingleData(湿度) → USART1 发 8 字节
时刻 0ms  ─── DGUSTask: DGUS_WriteSingleData(环温) → USART1 发 8 字节
时刻 0ms  ─── DGUSTask: DGUS_WriteSingleData(风速) → USART1 发 8 字节
时刻 0ms  ─── DGUSTask: osDelay(5000) → 进入阻塞态，CPU 让给其他任务

   ... 5 秒内，LoRaTask 运行了约 5000 次，ModBusTask 运行了 5 次 ...

时刻 5000ms ─── DGUSTask 被唤醒 → 重复上述 4 次写屏操作 → 再次阻塞 5 秒

七、潜在问题与改进建议

  1. 无接收超时保护：DGUS_WaitRecive 如果屏幕完全不回复，指针永远为 0，函数永远返回 REV_WAIT。触摸应答场景没问题（没有触摸就不应该回复），但将来如果有"查询-应答"型指令，需要加超时计数
  2. 缓冲区无回绕：rx1_pointer 直线增长，100 字节硬上限，建议改为环形缓冲区或加越界检查
  3. 发送失败未检测：Usart_SendString 不检查 HAL_UART_Transmit 的返回值（HAL_OK / HAL_TIMEOUT / HAL_ERROR），通信故障时静默丢失数据
  4. 触摸坐标硬编码：坐标值 0x29, 0x00 等直接写死在代码里，屏幕 UI 一旦调整布局就必须改代码。建议用宏定义集中管理
  5. 品种选择注释错误：第 101–112 行的注释全部写的是"品种选择-小麦"，实际 6 个按钮对应 6 种不同粮食，注释应标注正确品种名
